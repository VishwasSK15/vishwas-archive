VISHWAS // THE ARCHIVE
RECOMMENDED TECH STACK DOCUMENT
Production architecture for a cinematic, editorial, content-driven portfolioPrinciple: use modern tooling, but keep the product architecture intentionally small.
1. Executive Recommendation
The recommended stack is a Next.js-first TypeScript architecture with Tailwind CSS v4, Framer Motion, next-themes, GitHub's API for dynamic project data, optimized image delivery, and Vercel for deployment.
The key recommendation is not to make the portfolio technically complicated just because the visual experience is sophisticated. The site should feel advanced while the underlying architecture remains maintainable.
Recommended core stack
Framework: Next.js 16.x with App Router
UI: React 19.x
Language: TypeScript 5.x
Styling: Tailwind CSS v4 + project CSS variables
Animation: Framer Motion
Icons: Lucide React

Content/data: TypeScript content modules + GitHub API
Image pipeline: Next/Image
Validation: Zod where external data crosses the application boundary
Testing: Vitest + React Testing Library + Playwright
Code quality: ESLint + TypeScript strict mode + Prettier
Package manager: npm
Deployment: Vercel
Repository/CI: GitHub + GitHub Actions where needed

3. Architecture Philosophy
3.1 Static-first, dynamic where useful
Most of the portfolio is stable content and visual composition. It should therefore be rendered as efficiently as possible. Dynamic behavior should be introduced only where it creates real product value—most notably GitHub project data, theme state, and client-side interaction.
3.2 Server by default
Use Server Components for content-heavy and data-fetching portions. Use Client Components only for interaction, animation, theme state, menus, and browser-dependent behavior.
3.3 Avoid unnecessary backend infrastructure
This portfolio does not currently need a custom Express/Node backend, MongoDB database, GraphQL server, or CMS. Adding them would create operational complexity without a clear product benefit.
3.4 Design system before page-specific hacks
The five worlds should share primitives for typography, spacing, navigation, transitions, buttons, metadata, project presentation, and responsive behavior.

8. Animation — Framer Motion
Recommendation: Keep Framer Motion
Framer Motion is appropriate because the portfolio's differentiation depends partly on transitions and interaction.
Primary uses
Page/world transitions
Hero text and image reveals
World navigation transitions
Scroll-linked reveals
Hover states
Menu transitions
Subtle image movement
Important constraint
Animation should not become the architecture. Avoid putting large portions of the page behind client-side animation when a simple CSS transition or server-rendered structure would work.
Accessibility
Respect prefers-reduced-motion and provide reduced-motion variants for all non-essential movement.

13. GitHub Integration
Recommendation: Server-side GitHub API integration
Continue the existing GitHub data layer for username VishwasSK15.
Rules
Fetch public repositories.
Filter by the portfolio topic.
Sort by recently updated.
Revalidate approximately every hour.
Normalize API responses into internal Project/GitHubRepository types.
Handle rate limits and API failures gracefully.
Architecture
GitHub API → server-side data layer → validation/normalization → Projects components → UI
Do not expose unnecessary API logic directly inside client components.
14. Runtime Validation — Zod
Recommendation: Add Zod only at external boundaries
Zod is recommended for validating GitHub API responses or any future external data source. It should not be used to validate every internal object that TypeScript already guarantees.
Why
External APIs can change.
Runtime data is not protected by TypeScript.
A schema makes failures explicit and safer.

23. Fonts
Recommendation
Use a deliberate display/body font pairing rather than defaulting to generic developer-site typography.
If external font fetching causes build reliability problems, self-host the selected fonts. This avoids production build failures caused by network-dependent font downloads.
Rule
Typography is part of the brand. Choose fonts based on the final visual direction, not convenience alone.
24. Data & Backend Decision
No database initially
A database is not recommended for the current portfolio.
No custom backend initially
A standalone Express/Node backend is also not recommended.
When this decision changes
A private admin CMS becomes necessary.
The site requires authenticated content management.
Large dynamic datasets appear.
Interactive features require persistent user data.
A future product evolves beyond a portfolio.
25. CMS Decision
Recommendation: No CMS for V1
The archive currently contains a manageable amount of content. Local typed content is faster, more reliable, and easier to version with Git.
Future option
If content volume grows substantially, consider a headless CMS such as Sanity or Contentful. Do not introduce one preemptively.
26. Recommended Folder Architecture
A practical structure should separate routes, components, data, and design primitives.
app/ — routes, layouts, metadata, loading/error boundaries
components/ — reusable UI and world components
components/ui/ — small primitives
components/layout/ — navigation, world index, shell
components/worlds/ — world-specific shared pieces
components/projects/ — project presentation
lib/ — GitHub client, utilities, validation
data/ — typed static content
styles/ — global design tokens if needed
public/ — static assets
Keep the existing architecture where it already works; this is a target organization rather than a mandate to move every file immediately.
27. Environment Variables
Principle
Only secrets belong in environment variables. Public configuration does not need to be hidden.
GitHub token, if a token becomes necessary for rate limits: server-only environment variable.
Analytics key, if analytics are added.
Any future third-party service credentials.
Never expose private tokens through NEXT_PUBLIC_* variables.
28. Security
Keep external API credentials server-side.
Validate external API responses.
Avoid rendering untrusted HTML.
Do not store unnecessary personal data.
Use secure deployment defaults.
Keep dependencies updated without blindly upgrading production dependencies.
29. Performance Budget Philosophy
Keep the initial page lightweight despite large visual assets.
Prioritize above-the-fold content.
Avoid shipping large client-only animation libraries beyond what is necessary.
Use responsive image sizes.
Lazy-load deep-page media.
Prevent layout shift.
Measure mobile performance before adding visual effects.
The cinematic design should be achieved through composition and optimized media—not by shipping excessive JavaScript.

33. Development Workflow
Create a feature branch.
Build the design/component change using the existing system.
Run TypeScript checks and lint.
Run unit tests for meaningful logic changes.
Run Playwright for navigation or responsive behavior changes.
Review desktop and mobile layouts.
Open a pull request.
Use the deployment preview for visual QA.
Merge to main.
Vercel deploys production.
34. Final Recommendation
Keep the portfolio technically lean and visually ambitious. Next.js + React + TypeScript + Tailwind v4 + Framer Motion is already a strong foundation for the product.
The most important additions are not more frameworks. They are engineering discipline around external data validation, testing, performance, accessibility, and deployment.
Final stack
NEXT.JS + REACT + TYPESCRIPT + TAILWIND v4 + FRAMER MOTION + NEXT-THEMES + LUCIDE + NEXT/IMAGE + GITHUB API + ZOD + VITEST/RTL + PLAYWRIGHT + VERCEL + GITHUB
North-star engineering principle
Technically simple underneath. Visually exceptional on top.
